## 三、接入过程中值得记录的坑

1. **推理模型的 `max_tokens` 要给够**：新一代模型（DeepSeek v4 / MiMo / 本地思考模型）会把输出预算先花在
   reasoning 上，`max_tokens` 给小了会得到「HTTP 200 但 `content` 为空」。客户端建议 ≥256，
   或按各家文档关闭思考模式（网关会把这类私有参数原样透传）。
2. **本机服务常要求 API Key**（如 llama-server `--api-key`）。托管探活**不带**密钥，所以 `401`
   恰恰说明服务在应答；界面上会显示成 `HTTP 401（在跑，需鉴权）`。
3. **本地脚本的启动方式要确认**：`start.bat` 这类脚本可能不是当前正在运行的实例的启动方式
   （例如实际由别的运行时直接拉起）。lifecycle 里的「启动命令」决定了服务挂掉后怎么拉起来，
   配错了会在重启时换一套配置。
4. **停止策略要克制**：自带 `stop.bat` 常写 `taskkill /IM llama-server.exe`，会杀掉机器上所有同类进程；
   默认的「按端口」策略只终止占用该渠道端口的那个进程。

- 想让局域网内其它设备使用：控制台 → 设置 → 网络 → 服务 IP 改为 `0.0.0.0` 并保存。
  （`server` 模式需重启进程生效；托盘/桌面模式下会自动热重绑定。）
- 计价表默认为空，所以「预估费用」恒为 0；到「设置 → 计价」按每百万 token 填单价后即出现数值。
- 验收过程会产生真实用量（含为验证错误码而故意制造的失败请求），所以控制台初始成功率不会是 100%。

## 六、控制台修复记录（2026-09-19）

两个用户报的现象，根因都在「事件循环被流式路径占满」这一类问题上。

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 统计图表更新慢或压根不更新 | 仪表盘那个 15 秒轮询只把数据取回来、**从不重绘**；「用量统计」页根本没有轮询 | 数据指纹判断 + 就地重绘，5 秒一次，后台标签页暂停、切回补一帧 |
| 调用 API 时控制台打不开 | `ChatProxy.iter_chunks` 每收一块就把**已产出的全文重新拼接并重扫**来估算 token（O(块数 × 全文长度) 的纯 Python 字符循环），长回答直接把 event loop 占满 | 改成 `TokenCounter` 增量累加（O(总长度)），顺带给每块触发的 live tick 推送加 0.2s 节流 |
| （排查中发现的隐患）升级后控制台仍跑旧前端 | `/static/*` 不带任何缓存指令，浏览器按启发式新鲜度缓存数小时 | `/static/*` 改为 `no-cache`（ETag 回源，未变即 304），HTML 里的资源 URL 带 `?v=<前端文件 mtime>` |
| （用户报障）新建渠道点「创建渠道」没反应 | 渠道表单的托管开关被 `lifeToggle` 把 `<input>` 挪出原节点，保存时 `节点.querySelector('input').checked` 抛 TypeError；异常只进浏览器控制台，请求根本没发出去 | 开关直接按标签文字构造（`toggleInput(checked, text)`），状态一律用带空值兜底的 `toggleValue(节点)` 读；并加了全局错误提示，前端异常不再静默 |

**实测**（同一台机器、同一份压测脚本，4 路 400k 字符 prompt、每路 1202 个流式块）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 压测期间控制台首屏响应 p50 / 最大 | 2.1 ms / **6680.2 ms** | 1.7 ms / **1.8 ms** |
| 单路流式总耗时 | 8.19 s | 0.15–0.30 s |

离线回归：`python -m pytest tests` → **179 passed**（本节修复期间新增 8 条：模型预览 3 条 + 模型目录 2 条 + 前端约定 3 条）。

### 模型名下拉（同日追加）

用户提的三件事：白名单要能看到**所有**模型、新建渠道时就允许拉上游列表、下拉按**渠道**分组。

| 需求 | 做法 |
| --- | --- |
| 白名单显示所有模型 | 新增 `GET /api/admin/models/catalog`：按渠道分组返回「该渠道白名单 ∪ 该渠道上游真实 id」，带取回时间与**逐渠道**的失败原因（一个渠道拉挂了不影响别的组）。结果缓存在内存里，TTL 走设置项 `services.catalog_ttl_seconds`（默认 600 秒）；面板里的「刷新上游模型」才强制实时拉 |
| 新建渠道时拉模型 | 新增 `POST /api/admin/channels/models/preview`：直接用表单里**还没落库**的 `base_url` / API Key 问上游要列表，所以渠道不存在也能拉；改已有渠道未保存时 `api_key` 留空会沿用库里那把 |
| 下拉显示渠道模型 | 自绘的 `modelPicker`：输入框点开是按渠道分组的面板，组标题标「上游可用 N 个 / 上游列表没拉到：原因 / 已禁用」，支持过滤、↑↓ 选 + 回车加、通配符照旧手输 |

> 单独说明一处**已保存渠道**的写入方式：渠道行「白名单」弹窗里点模型是加进内存草稿，**关弹窗时合并成一次 `PUT`**。之前每个模型发一次 `PUT`，上游列表几十条时既慢又会刷出几十条提示；现在「加入 N 个」只落一次库、只出一条提示，且没有任何改动时不会发请求。

实测（真实上游，本机 5 个渠道）：面板分组显示 DeepSeek 官方 2 个、星火本地 2 个、本地模型 8090 10 个、
小米 MiMo 6 个、智谱 GLM 11 个，共 43 个候选；过滤 `qwen` 命中 1 组 6 个候选；手输 `mimo-v2.5-*`
回车按原样收成标签（通配符未被打散）；未保存的新渠道拉取得到 10 个模型、「全部加入」填 10 个标签、
取消后渠道数不变（未落库）；已保存渠道「全部加入」→ 1 次 `PUT`、1 条提示，白名单与刷新后的列表一致。

### 顺手修掉的健康徽记误报（同日追加）

排查上面几项时在截图里发现：DeepSeek / GLM / MiMo 三个渠道挂着红色「失败 ×1」，但同一时刻
DeepSeek 刚跑通一次真实请求（`last_ok_at` 比错误时间更晚）。根因是徽记的判据写成了
「`last_error` 非空」——而这个字段是**故意**不在成功时擦掉的（留给排障看原文），于是上游一次
忙、或用户发过一张上游不认的图片，那条错误就会永久把渠道标成失败。改成比较时间先后
（`channelFailing()`：错误比最近一次成功更新、或压根没成功过，才算真在失败），并把错误原文与
发生时间放进徽记的悬停提示里——此前 `last_error` 在界面上根本没有露出，README 里却让人
「看渠道的最近错误」，两边对不上。

实测：上述三个带历史错误的渠道现在显示「正常」（悬停仍能看到历史错误与时间）；另建一个指向
死端口的临时渠道跑一次真实请求，徽记按「冷却 58s → 失败 ×1」演进，悬停显示错误原文与发生时间；
验完删除该临时渠道，渠道列表恢复为原来的 5 个。
